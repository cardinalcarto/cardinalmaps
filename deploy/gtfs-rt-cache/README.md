# GTFS-RT cache updater

One always-running Fly Machine refreshes feeds from the current published transit
release. It reads `releases/latest.json`, then that release's `realtime.json`
(the existing feed index generated by `valinor-transit-build`). It uses every
listed URL, regardless of feed kind, deduplicating identical upstream URLs.
If a manifest request fails, the previous list stays in use.

Every 60 seconds the updater attempts a refresh of each feed in parallel, with
bounded concurrency and timeouts. Slow rounds do not overlap; large deployments
can tune `GTFS_RT_WORKERS` and the Machine's memory. The updater validates the
protobuf and publishes the original bytes, without re-encoding them. Failed
requests, invalid messages, and failed uploads leave the preceding object in
place. Objects are not deleted during outages.

Each object is public-read at:

```
https://cardinal-carto-public.t3.storage.dev/gtfs-rt/<sha256 of exact manifest URL>.pb
```

The `x-amz-meta-fetched-at` response header is the Unix timestamp (seconds) of
the successful upstream download. `Cache-Control: no-cache` allows revalidation
without serving an outdated object as a fresh one. Clients reject objects with
missing or expired timestamps, and the planner independently expires their
contents 180 seconds after the successful fetch, even without a new download.
Agency GTFS-RT header timestamps have separate freshness limits: 10 minutes
for trip updates, vehicle positions, and combined feeds, and 30 minutes for
alerts. Clients check for new objects on demand at most once per minute,
never querying agencies directly.
Old pinned releases continue to work for URLs still listed in the latest
release; removed or changed URLs age out rather than fetching upstream.

## Deploy

The Images workflow publishes `cardinal-gtfs-rt-cache` to GHCR with both `main`
and `sha-<short commit>` tags. It does not deploy. Set the image in `fly.toml`
to the desired immutable tag, create the application, and configure write
credentials for the existing `cardinal-carto-public` Tigris bucket:

```sh
fly apps create cardinal-gtfs-rt-cache
fly secrets set AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... -a cardinal-gtfs-rt-cache
fly deploy -c deploy/gtfs-rt-cache/fly.toml --ha=false
fly scale count 1 -a cardinal-gtfs-rt-cache
```

There is no listening service or HTTP traffic-based stopping; the machine must
stay running, and only one instance should run. Use a bucket-scoped credential
with permission to put objects under `gtfs-rt/`. The bucket already allows
public reads. No credentials are needed on clients.

For another environment, `RELEASES_URL`, `BUCKET_NAME`, `AWS_ENDPOINT_URL_S3`,
and `AWS_REGION` override the defaults. The production app uses the public
bucket URL above. To run mocked tests locally, install `requirements.txt` and
run `python -m unittest test_updater` from this directory.
